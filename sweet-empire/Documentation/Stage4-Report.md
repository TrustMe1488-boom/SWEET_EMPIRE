# SWEET EMPIRE — отчёт этапа 4

Реализовано в существующем проекте Godot 4.7.2 / GDScript / Compatibility, Windows PC. Этап 5 не начинался. Git-команды не выполнялись. Изучены родительский AGENTS.md, README, существующие скрипты и отчёты предыдущих этапов. Более позднее явное разрешение пользователя на этап 4 заменяет историческую отметку «0B» в AGENTS.md.

Перед изменениями сохранены 162 исходных файла в `Documentation/backups/stage4/`; SHA-256 — `manifest.json`. Все прежние тесты побайтово сохранены. Цены, производство, вместимость, FIFO, ручная доставка, найм, улучшения и условия победы не менялись.

## 1. Utility AI и типы покупателей

`CustomerUtilityAI` встроен в существующий `BakeryGame.spawn_customer()`. Он создаёт прежний `CustomerOrder`; далее работают прежние CustomerController, QueueManager, CashierController и SaleProcessor. Параллельного потока заказов нет. Старый OrderSelector сохранён как совместимый API для прежних изолированных тестов; игровой поток использует Utility AI.

Общий источник конфигурации Godot/Python: `assets/ai/customer_profiles.json`.

| Тип | Терпение | Доля смешанного потока | Вес: печенье / кофе / капкейк / торт |
|---|---:|---:|---|
| NORMAL | 20 с | 50% | 1 / 1 / 1 / 1 |
| IMPATIENT | 10 с | 25% | 1,6 / 1,3 / 0,7 / 0,4 |
| SWEET_TOOTH | 25 с | 25% | 1 / 0,6 / 1,8 / 2,2 |

Допустимы только продукты купленных станций с поваром. Готовый запас не участвует в фильтрации: отсутствующий на кассе продукт всё равно может быть заказан. В Rush utility дополнительно умножается на `1 + 0.15 × 4 / BaseTime` — небольшое предпочтение быстрых изделий; цены не меняются. Положительные конечные веса нормализуются, затем применяется weighted random. Некорректные веса обнуляются, полностью нулевой набор заменяется равномерным. Пустой ассортимент не создаёт заказ. Нулевой вес не выигрывает даже при roll=0.

Первые три гостя — NORMAL для постепенного знакомства; затем включается смешанный поток. Первый учебный гость по-прежнему защищён от таймаута и штрафа. Фиксированный RNG воспроизводит тип и заказ. После создания заказ неизменяем, замена товара и повторная продажа запрещены прежними проверками.

Rush умножает **базовое терпение конкретного типа** на 1,2: 24 / 12 / 30 с. Уже ожидающие гости получают дополнительные 20% своего базового терпения. Защита учебного гостя сохраняется. Тип, базовое и оставшееся терпение включены в контрольную точку.

## 2. Сбор данных

`DemandDataCollector` отслеживает созданные заказы, тип/продукт/ID гостя, продажи, уходы и существующие игровые события вместе с рейтингом, главой, ассортиментом, временем и режимом Rush. Целевой спрос — **все созданные заказы**, включая впоследствии необслуженные. При заполненной очереди новый заказ не создаётся и не считается спросом принятого потока.

Время продвигается только игровым delta, пауза его останавливает. Для признаков хранится история 120 секунд; для явного экспорта — журнал сессии в RAM. Персональные данные не собираются; нет имён пользователя, телеметрии в сеть или автоматической записи прогресса на диск. Кнопка CSV в аналитике явно записывает `user://demand-events.csv`.

Контрольная точка Rush содержит журнал, окно истории, часы, последний прогноз и момент обновления. Неудачная попытка откатывает их вместе с прежними игровыми данными, поэтому отменённые события не загрязняют последующий экспорт.

## 3. ML: данные, признаки, обучение

Python используется **только офлайн**. Для игры не нужны Python, numpy, pandas или sklearn. Скрипты находятся внутри проекта в `Tools/ML`; `.gdignore` исключает их и датасет из импорта Godot.

Генератор создал **240 независимых синтетических сессий, 7440 окон**. Сессии моделируют главы, ассортимент из 1–4 купленных/укомплектованных станций, рейтинги 1–5, обычный интервал `uniform(8,10)/F_rating`, Rush `uniform(3,4)`, три типа гостей, FIFO максимум 5, терпение, автоматическое производство, запас станции 5 и периодическую ручную доставку партиями максимум 5. Синтетический Rush длится 90 секунд; будущие окна включают его завершение. Колебания возникают из случайных интервалов, типов, weighted заказов и темпа доставки.

Разделение **по session ID**: 144 train / 48 validation / 48 test, соответственно 4464 / 1488 / 1488 строк. Пересечения сессий нет; перекрывающиеся окна одной сессии не попадают в разные выборки. Цель: количество заказов каждого продукта в строгом будущем интервале `(t, t+120]`. Признаки используют только события `<=t`.

21 признак в строгом общем порядке:

- рейтинг, глава;
- четыре флага доступности, Rush;
- четыре количества заказов за последние 120 с;
- общее число заказов за 30 с;
- оценка интенсивности `N120 / clamp(session_time, 30, 120)`;
- три доли типов в недавней истории (нули без истории);
- время с начала сессии;
- четыре causal opportunity-признака: ожидаемый поток за 120 с, рассчитанный из текущего рейтинга/режима, доступности и общей конфигурации предпочтений.

Opportunity — аналитический **входной признак**, а не выданный за ML готовый ответ. Итоговые коэффициенты Ridge реально обучены по наблюдаемым будущим заказам; ручных коэффициентов прогноза нет. StandardScaler обучен только на train. Округление происходит только при выводе. Короткая история использует минимум 30 с в знаменателе интенсивности: иначе несколько начальных событий давали завышенную частоту.

Сравнены Ridge с пятью alpha и RandomForest (60 деревьев, depth9, leaf15). Выбор — **Ridge_10**, по validation MAE среди совместимых с компактным линейным экспортом моделей. RandomForest тоже оказался хуже выбранной Ridge.

| Кандидат | Validation MAE | Validation RMSE |
|---|---:|---:|
| Ridge_0.1 | 0.8322 | 1.2794 |
| Ridge_1 | 0.8318 | 1.2789 |
| Ridge_10 | 0.8308 | 1.2771 |
| Ridge_100 | 0.8330 | 1.2772 |
| Ridge_1000 | 0.8516 | 1.3035 |
| RandomForest | 0.8643 | 1.3231 |

## 4. Качество на отдельных тестовых сессиях

Baseline A — средний спрос **по такому ассортименту и режиму** на train (более сильный вариант простого среднего). Baseline B — количества заказов предыдущих 120 с, перенесённые на следующие 120 с. Во всех случаях недоступные продукты обнуляются.

| Продукт | ML MAE | ML RMSE | A MAE | A RMSE | B MAE | B RMSE |
|---|---:|---:|---:|---:|---:|---:|
| Печенье | 1.1857 | 1.5516 | 1.3797 | 1.7192 | 1.9718 | 2.6788 |
| Кофе | 1.0866 | 1.4483 | 1.1883 | 1.5708 | 1.6485 | 2.2595 |
| Капкейк | 0.6323 | 1.1442 | 0.6645 | 1.2074 | 0.9476 | 1.6920 |
| Торт | 0.3862 | 0.9304 | 0.3817 | 0.9530 | 0.6008 | 1.4434 |
| **Среднее** | 0.8227 | 1.2686 | 0.9036 | 1.3626 | 1.2922 | 2.0184 |

Средние метрики — арифметическое среднее четырёх продуктовых метрик. ML улучшает общий MAE примерно на 8.9% к A и на 36.3% к B. **Для тортов MAE 0,3862 немного хуже A=0,3817**; скрывать это или заявлять улучшение каждого продукта нельзя.

Это качество на синтетических данных, **не гарантия точности на настоящих игровых сессиях**. Машиночитаемые результаты: `Tools/ML/artifacts/metrics.json`, эксперименты — `experiments.json`, происхождение датасета — `dataset_metadata.json`.

Ранний эксперимент использовал постоянный Rush за пределами 90 секунд; это обнаружено и исправлено, ранние метрики не используются. При отладке также исправлены остановка синтетического производства при полном запасе и обработка холодного старта. Финальная модель переобучена и проверена.

## 5. Экспорт и runtime

`export_model.py` экспортирует `assets/ai/demand_model.json`: version1, schema_version1, точный порядок 21 признака, продукты, horizon120, mean/scale, 4×21 обученных коэффициентов, четыре intercept и метаданные алгоритма/seed/источника. `trained.pkl` нужен только для офлайн-повторения экспорта, игра его не читает.

`DemandPredictor` выполняет `(x-mean)/scale`, четыре линейных скалярных произведения, clamp>=0 и маску текущей доступности. Проверяются версия, горизонт, порядок продуктов/признаков, размеры, числовые конечные значения и положительность scale. Отсутствующий, повреждённый или несовместимый JSON безопасно включает **fallback**: равномерное распределение ожидаемого потока среди доступных продуктов. Источник отображается явно как ML либо fallback.

Обновление раз в 30 **игровых** секунд; дополнительно немедленно после изменения развития/найма и входа/выхода из Rush. При паузе таймер не продвигается. После отката попытки восстановленная история пересчитывается. Обучение в Godot не запускается.

В ней четыре настоящих значения DemandPredictor, timestamp игрового времени, полосы спроса, предупреждение и CSV-экспорт. Учитываются касса, поднос, станции и ассортимент. Текст маркирует правила отдельно от прогноза. Это пассивное сообщение по открытию панели, без навязчивых всплывающих уведомлений.

## 8. Проходимость кампании

Повторная детерминированная симуляция seed20261114 прошла от **0 монет до естественной победы**, без тестового финансирования:

- кофемашина: 118,50 с; повар кофе: 181,75 с;
- глава2: 181,50 с; глава3 и обычная Zone3: 593,50 с;
- Rush начат на 1618,75 с после подготовки кассы; 15 обслуживаний за **56,75 с**;
- победа на **1675,50 с (27:55,5)**;
- обслужено206; выручка4750; баланс1910; кристаллы195; уходов0;
- все 9 заданий и 6 достижений достижимы; отрицательного баланса нет.

Драйвер учитывает длительность пути Мии через дверные точки при 4м/с и вызывает реальные взаимодействия E после прибытия. Производство, FIFO, терпение, кассир, цены, задания и кампания настоящие. Это автоматическая экономическая симуляция с позиционированием по окончании пути, **не полное ручное прохождение и не непрерывный физический pathfinding-тест**. Ввод WASD отдельно проверен реальными physics-кадрами прежних тестов. Другие seed могут давать иной результат; общая гарантия проходимости любой стратегии не заявляется.

## 11. Запуск и повторное обучение

Откройте **существующий** `project.godot`, F5 → «Начать игру». Пройдите обучение. Дальше кнопка Софи или Tab → «Аналитика»; Esc возвращает в игру. WASD/E/1/2 и все прежние меню сохранены. Для обычной игры установка Python не требуется.

Из корня проекта, PowerShell:

```powershell
python -m pip install --target .local/ml-python -r Tools/ML/requirements.txt
python Tools/ML/generate_dataset.py
python Tools/ML/train_model.py
python Tools/ML/evaluate_model.py
python Tools/ML/export_model.py
python Tools/ML/test_pipeline.py
```

Для реальных данных экспортируйте **разные полные сессии**, минимум10 файлов, затем `python Tools/ML/build_real_dataset.py path1.csv ... path10.csv`. Результат `Tools/ML/artifacts/real_dataset.csv`; обучение: `python Tools/ML/train_model.py --dataset Tools/ML/artifacts/real_dataset.csv`, затем evaluate/export. Конвертер отбрасывает хвост без полного будущего горизонта, не делит одну сессию между выборками. Историческую синтетическую модель следует копировать перед её заменой. Команда обновлённого train по умолчанию возвращает обучение на синтетическом dataset.csv.

Godot-проверки: закройте другие экземпляры Godot **для этого проекта** и запускайте последовательно `--headless --path . --script tests/<suite>.gd`; имя executable зависит от установленного пути. Не запускайте два экземпляра одновременно. При подготовке экспортируемой Windows-сборки добавьте `assets/ai/*.json` в фильтр включения не-ресурсных файлов; бинарный экспорт Windows в этом этапе не проверялся.

Критических ошибок загрузки/игрового runtime в выполненных проверках не обнаружено. Ограничения:

- только синтетическое качество; пока нет оценки на репрезентативных настоящих сессиях;
- синтетика использует дискретную FIFO/доставку без геометрии, фиксированный рейтинг/ассортимент внутри сессии, без интерактивного обучения; реальный игрок может вести себя иначе;
- модель не знает будущих покупок/открытия зон, оставшегося времени Rush и планов доставки; это ограничивает прогноз около переходов;
- небольшое уступание baseline A по MAE тортов, приведено выше;
- нет доверительных интервалов; сумма — ожидаемые заказы, а не гарантия продаж;
- журнал событий в RAM растёт в течение сессии; CSV только по явному нажатию, никаких автосохранений;
- массовые multi-seed прохождения, длительный стресс-тест, экспорт exe и ручное полное прохождение не выполнялись.

Рекомендации после разрешения следующего этапа: собрать реальные сессии и повторить session-split оценку, проверить несколько стратегий/seed кампании, исследовать известное оставшееся время Rush как causal-признак новой версии схемы, отдельно улучшить MAE тортов и сделать более длинные performance-прогоны. Косметика, ML в выборе заказа, новые станции и автоматическая доставка не добавлялись.
